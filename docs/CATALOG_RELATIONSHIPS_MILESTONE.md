# Catalog relationships and purchasing controls

October 17, 2026. Implements the agreed catalog/manufacturer/translator/MRF portion under the owner's scoped development authorization. **Any addition that incurs costs or subscriptions requires the owner's express approval before commitment, throughout this development.** This authorization is not permission for unrelated future features. No paid service, subscription, AI/search activation or DNS change was made in this milestone.

## Implemented behavior

- Canonical materials have category-specific structured attributes and a deterministic identity. Equivalent structured records reuse the same material, including concurrent insert attempts; manufacturer brands do not participate in that identity. Meaningful differences remain separate. Manufacturers and their part numbers live in linked manufacturer-product records, with uniqueness per manufacturer/part number. Existing legacy records/draft references are retained, not automatically merged.
- Initial description templates cover conduit/pipe, telescoping brackets, boxes and a general specification. Required facts must be supplied; missing dimensions are rejected instead of guessed. All numeric dimension fields use inches. Actual bracket span and optional nominal spacing are separate. Future category templates and the final launch exchange format remain adjustable.
- Searches preserve explicit manufacturer/part intent and group products under their material. An exact part number sorts its product ahead of the ordinary preferred product. High-use designation and selection frequency boost relevant, otherwise equally ranked results; ten recorded selections qualify a material as high use. Explicit specification/brand constraints take precedence.
- Deterministic search supports the discussed `10' Stick PVC 40` example without a model call, returning multiple diameters rather than assuming one. Structured fractional-inch sizes, pipe/conduit distinctions, schedule differences and bracket span containment are tested. These initial category rules do not claim universal engineering equivalence.
- Adding a catalog result to an MRF records a selection event and potential translation immediately, not after PO reconciliation. Original phrase, actor, project and time are retained. Retrying an event is idempotent; a phrase can link to multiple materials. Admins can reject a translation without erasing history; a rejected relationship is not automatically reactivated by another click. Phrase learning currently accepts up to 500 characters; longer descriptions remain usable for an MRF but are not automatically learned.
- MRF result choices and the edit dialog expose manufacturer products. A preferred product is a purchase example; it does not silently enable No Substitutions. The edit dialog supports manual manufacturer/part details and an explicit No Substitutions flag requiring both. Saved lines retain manufacturer/part/product-ID snapshots. The server validates product ownership and rejects forged relationships. Historical unchanged product snapshots can still be saved after product deactivation; the readiness check flags retired/invalid choices.
- Job allow lists support manufacturers and/or exact products at job, category or material scope. Restrictions default inactive. Active applicable rules intersect; when both manufacturer and product lists are populated, both must match. Searches filter product choices with job context, the edit dialog disables disallowed catalog choices, and the server readiness check flags conflicts. Drafts are preserved rather than silently changed or discarded. Admins can deactivate rules. UI creation currently emphasizes material-specific product lists; the API supports the other scopes.
- **There is still no purchasing submission workflow.** “Check purchasing requirements” performs a server check and submits nothing. A future submission endpoint must run these validations again atomically before commitment; the client-side display alone must never authorize purchasing.
- Generic material and exact manufacturer-product images have separate approval scopes. Administrators choose the scope before upload. A generic approval does not approve a branded product photo, and one product approval does not replace another scope. Existing normalization/rights review/private storage controls remain. The same canonical bytes cannot be assigned to a different scope for the same material through this pilot; the API explains the conflict instead of silently moving the photo.

## AI discovery boundary

A transactional selected-discovery ingestion operation is implemented for a future discovery provider. It reconciles structured identity, links manufacturer/part details, records the user's selection, and accepts up to eight supplied alternative phrases. New AI-sourced material/product records always enter provisional status. Generated phrases retain AI origin and evidence; unsupported numbers, markup and terminology are rejected. Human administrators can separately verify material specifications and product equivalence with explicit review statements and audit history. Importing a batch does not perform those reviews.

This boundary makes **no model or web request** and does not fabricate discovery results. There is no live discovery provider or user-facing live product-discovery list yet. Automatic generation/retrieval requires that future provider integration and separate approval before any new costs. The existing optional model clarification client and all external search remain off. Tests use synthetic source URLs and product information, not verified Caddy data. The TSGB1624/TSGB1426 identifier discrepancy remains unresolved; neither was inserted as a real verified product.

## Bulk import support

The new staged importer supports material, manufacturer product, translation and image-reference records. Current development CSV has two columns, `kind` and `data_json`; one kind per file. This is a working adapter, **not a demand that the owner's future AI dataset use a finalized format**. Load materials first, then dependent products/translations/image references using stable material keys. If an equivalent material already exists under a different key, use the existing key for later stages; do not invent a second identity. Exact columns/adapters can be agreed later.

Each file is limited to 800 KB and 2,000 rows. Preview validates row fields/references, reports actual CSV row numbers, and detects repeated rows. A preview can be refreshed after fixing referenced data. Apply revalidates in a transaction and requires explicit administrator confirmation. Repeat content/application does not duplicate relationships. Batch rollback deactivates only the records it created; no physical deletion of historical references. Independently learned translations retain their separate provenance after imported phrases are rolled back. Referenced products/materials are retained as inactive records, and affected drafts require readiness review.

AI source kinds are explicit. Use `origin: ai_import` and `verification: provisional` for AI-created material/product data; AI phrases use `ai_import`/`ai_generated` plus an evidence URL. An operator's review of import mechanics is distinct from factual verification. The legacy v1 CSV importer is retained for local regression fixtures; new real catalog uploads through the HTTP API must use structured identity-aware imports. The legacy export is not a complete export of new relationships; a final exchange/export contract is still future work.

Image-reference imports preserve source URL, usage rights and optional manufacturer product link in a pending queue visible to admins. They do not fetch, approve, or grant rights to remote images. Actual files use the existing reviewed upload workflow.

## Persistence and validation

New forward migrations add material profiles, manufacturers/products, translations, selection history, job restrictions, structured batches, image references and line snapshots. Original migration checksums remain unchanged. Local SQLite, restricted SQL Server setup and Azure migration source all run/verify the added migrations; runtime identities receive table permissions, not DDL or audit-delete rights.

Verified with strict production/type/server builds, 34 backend tests, 18 real SQL Server tests, and 39 browser tests. Shared scenarios cover simultaneous identity/product insertion, tenant/role boundaries, forged snapshots, provisional-to-reviewed boundaries, explicit-brand/range/fraction matching, inactive/active rules and scoped photos. A 1,000-row translation batch applied and rolled back on both engines; this is staged pilot evidence, not a claim of large enterprise catalog performance. Search currently scans tenant materials/translations/products; indexing/paging/load targets should be revisited once launch volume is known. Admin overview/history views also need paging for sustained high volume.

The native SQL backup/checksum/restore/CHECKDB drill includes the new relationship table counts. The full browser suite includes responsive MRF, accessibility, offline preview, image review, manufacturer preference, learning, and saved No Substitutions lines. A startup project-switch race was fixed. API throttles now return JSON and allow 1,800 requests/minute per IP plus 600 per authenticated account, accommodating image-heavy drafts; upload and persistent AI caps remain separate. These are abuse controls, not a billing cap.

Azure hosting still awaits B1 quota support request `2610170040001486`. Real Entra sign-in, Azure SQL/Blob managed identity, cloud recovery and any paid AI provider require live acceptance. This work made no Azure calls or new spending commitments.
